# Baseline: Business Applications — Architecture & Stack
Status: draft      Date: 2026-08-19

## Category definition (working boundary)

"Business application" = a multi-tenant or single-tenant SaaS/enterprise CRUD system with a persistent database, a UI that end-users and business operators directly interact with, and typically both a backend AND a frontend under one product. Examples: B2B SaaS product, internal back-office/admin tool, ops dashboard, CRM-style app. Distinguished from **Backend & API Services** (already baselined) by owning the UI layer, not just exposing an API for other systems.

## In scope

- **Default architecture pattern: modular monolith** — impact: high — depth: section
  Confirmed (not just assumed) as the honest default for this category at typical starting scale. Rationale below is not generic — it's about *why this category specifically* lands here, tied to team-size and module-boundary signals (multi-tenancy, RBAC, billing, notifications, reporting are naturally separable modules from day one, which is what makes "modular" tractable even inside one deployable).
  - Decision rule to carry into the skill: start modular monolith; extract a service only when a **concrete, named forcing function** appears — independent scaling need for one module (e.g., report generation is CPU-heavy and needs to scale independently of the request path), a compliance boundary requiring physical data/process isolation, or a second team that needs to own and deploy a module independently. "We might need to scale later" is not a forcing function.
  - Team-size signal (qualitative, deliberately not a number): the coordination overhead of microservices — cross-service contracts, distributed debugging, N deployment pipelines — only pays off once there are enough independent teams that the monolith's shared-codebase coordination cost exceeds it. Below that point a monolith (modular or not) consistently ships faster. This research turned up only SEO-aggregator content proposing specific numeric team-size thresholds (e.g., a "127% modular-monolith adoption growth" stat and specific headcount cutoffs) with no identifiable primary source — excluded per the research standard's instruction to drop unsourced stats rather than launder them through a citation. Carry the forcing-function framing (a named second team needing independent deploy ownership) into the skill instead of a number.
  - How this specializes architecture-templates.md: business apps almost never need event-driven/CQRS or serverless as the *primary* architecture — those apply as targeted techniques (e.g., CQRS for a reporting module with heavy read/write asymmetry, event-driven for cross-module notifications) layered inside the modular monolith, not as the top-level shape. Microservices become the default only once the team-size/compliance forcing functions above are met — this is a genuine, not generic, divergence from a backend-services default where independent deployability may matter sooner.

- **Multi-tenancy architecture** — impact: high — depth: section
  Three real patterns exist on a spectrum from shared-everything to shared-nothing; the fourth "pattern" often listed (RLS) is an enforcement mechanism that can be layered onto the shared-schema pattern, not a separate tier.
  1. **Shared schema + row-level isolation (`tenant_id` column + app-layer or DB-layer filtering)** — lowest cost, single migration path, fastest tenant onboarding (one row insert). Real risk: a missed `WHERE tenant_id = ?` is a data breach, and "noisy neighbor" tenants degrade others sharing the same tables/indexes. Mitigation with a concrete tool: Postgres native Row-Level Security (`CREATE POLICY ... USING (tenant_id = current_setting('app.tenant_id'))`) moves the isolation enforcement into the database so an app-layer bug can't leak data — but only works correctly if the app connects as a non-superuser role (superusers bypass RLS) and every write path sets `WITH CHECK` in addition to `USING` (USING gates reads; a policy missing WITH CHECK only protects reads, not writes). This is the correct default for most B2B SaaS starting out — hundreds to low-thousands of tenants on shared infra.
  2. **Schema-per-tenant** — one Postgres database, one schema per tenant, app routes queries by switching `search_path`/schema based on tenant context. Stronger isolation than shared-schema (a query can't cross schemas by accident), still one physical database to operate/back up. Cost: migrations must run per-schema (N schemas = N migration runs), and connection/schema-routing logic adds real operational complexity once tenant count reaches the high hundreds to low thousands. `django-tenants` (Django/Postgres) is the concrete, verified tool for this pattern.
  3. **Database-per-tenant** — full physical isolation: clean per-tenant backup/restore/export, easiest story for regulatory data-residency requirements (a specific tenant's data can live in a specific region/instance), trivial tenant offboarding (drop the database). Cost scales roughly linearly with tenant count — connection pooling across N databases, N-way migration orchestration, and provisioning latency all become real engineering problems past dozens to low-hundreds of tenants. Reserve this for: enterprise tenants with contractual/regulatory isolation requirements (healthcare, finance, government), or tenant counts low enough (tens, not thousands) that per-tenant infra is affordable.
  - **Decision rule to carry into the skill**: default to shared-schema + Postgres RLS. Move to schema-per-tenant only when a compliance/audit requirement demands schema-level separation without full database-per-tenant cost. Move to database-per-tenant only when a named tenant contract or regulation (not a hypothetical) requires it, or tenant count is small enough that per-tenant cost is a non-issue.
  - This is the sub-topic where the guidance most differs by scale — must be called out explicitly in the authored skill, not flattened to one recommendation.

- **Frontend architecture for business apps** — impact: high — depth: section
  The category-specific nuance vs. a general frontend-architecture reference: business apps are almost always **fully authenticated, behind a login** — this changes the calculus that drives public-facing SSR/SEO recommendations elsewhere.
  - For a fully authenticated, non-SEO-relevant surface (the overwhelming majority of admin panels, internal tools, back-office CRUD), a client-rendered SPA (React + Vite, or React Router in framework mode without server rendering) remains a legitimate, simpler choice — no server-rendering infrastructure, no hydration-mismatch class of bugs, straightforward client-side auth/routing.
  - Where React Server Components (Next.js App Router) earn their complexity in this category specifically: dashboards with first-load-heavy data (the server fetches with the session cookie already available, avoiding client fetch waterfalls after a blank shell), or products where marketing/signup pages share a codebase with the authenticated app and genuinely need SEO — a common shape for SaaS (marketing site + app in one Next.js repo).
  - Trade-off to state honestly: RSC/App Router adds real operational complexity (hydration model, server/client component boundary discipline, caching semantics that have changed across Next.js versions) that a pure back-office tool with no public/SEO surface does not need to take on.
  - htmx/server-rendered-HTML-over-the-wire is a legitimate lower-complexity alternative specifically for CRUD-heavy internal tools (less client JS, simpler mental model) — worth naming as an option, but do not cite specific "% code reduction" figures found in the research (multiple sources claimed 40-60% JS reduction with no identifiable primary benchmark — excluded per research standard).
  - **Decision rule to carry into the skill**: default SPA for internal/back-office tools with no public or SEO surface; default Next.js App Router (RSC) when the same codebase serves a public/marketing surface alongside the authenticated app, or when first-load dashboard performance with heavy server-side data is a named requirement.

- **Auth / RBAC / permission-model architecture** — impact: high — depth: section
  - RBAC (role → permissions, e.g., "admin", "editor", "viewer") is the correct starting default: cheap to implement, easy to reason about, and matches how most business apps actually onboard users (assign a role at invite time).
  - ABAC (attributes of user + resource + environment, e.g., "manager can approve requests from their own department, only during business hours") is needed when permission logic depends on data that isn't captured by a role alone — org hierarchy, resource ownership, time/location constraints, or per-record exceptions. This is a real, common outgrowth in B2B SaaS once customers ask for "can user X see only their team's records" — a request RBAC alone cannot express cleanly.
  - **Decision rule to carry into the skill**: start RBAC. Introduce ABAC/policy-based rules incrementally, scoped to the specific resource types that need attribute-based logic (ownership, department scoping), rather than replacing RBAC wholesale — the common real-world pattern is RBAC for coarse role gating plus a small number of attribute-based rules layered on top (e.g., via a policy library — see libraries.md), not a full ABAC rewrite.
  - Multi-tenant-specific wrinkle this category must call out: role scoping needs a tenant dimension from day one ("admin *within tenant X*", not "admin" globally) — a common early-stage bug is treating roles as global when they're actually per-tenant.

- **Background job / async-task architecture** — impact: high — depth: section
  Business apps have a small, recognizable set of async needs: report/export generation, transactional + bulk email, scheduled/recurring jobs (billing runs, reminders, digest emails), and webhook delivery/retry.
  - Architecture pattern, not just tool choice: separate the request path from anything that (a) takes >1-2s, (b) needs retry-on-failure semantics, or (c) runs on a schedule. Push these to a queue + worker process, never inline in the request/response cycle.
  - The category-specific decision is queue-backed library (self-run workers, e.g., BullMQ/Celery/Sidekiq) vs. managed durable-execution platform (Inngest/Trigger.dev) — see libraries.md for the concrete trade-off; the architectural point to make here is that a *durable-execution* model (steps individually retriable, resumable across deploys) is increasingly the right default for business-workflow jobs specifically because business workflows (multi-step approval flows, onboarding sequences) benefit from step-level durability more than raw throughput.

- **Audit logging as an architectural concern** — impact: med-high — depth: section
  Business apps (especially B2B SaaS selling into regulated or enterprise buyers) routinely need "who did what, when" as a first-class, queryable record — not just application logs.
  - Two real implementation shapes: (1) a dedicated append-only `audit_log` table/service that every mutating action writes to explicitly (simplest, works with any architecture, easy to reason about and query) vs. (2) full event sourcing, where the event log *is* the source of truth and current state is derived from it (strong audit guarantee "for free," but a much bigger architectural commitment — changes how every write path and every read model works).
  - **Decision rule to carry into the skill**: default to the dedicated audit-log-table approach for the modular-monolith default in this category — it delivers the compliance/audit requirement without forcing an event-sourcing rewrite of the whole data model. Reserve full event sourcing for cases where temporal queries ("what did this record look like on date X") or event replay are themselves product requirements, not just an audit nice-to-have.
  - Minimum fields a baseline audit log needs (actor, tenant, action, resource, before/after or diff, timestamp, request/correlation id) is worth stating as a checklist item in the authored skill.

- **Admin-panel / back-office tooling: build vs. buy/generate** — impact: med — depth: section
  - Batteries-included frameworks (Django, Rails+Avo/ActiveAdmin, Laravel+Filament) ship a first-party or near-first-party admin generator that reads the data model and produces working CRUD screens with auth already wired — for these stacks, using the built-in/first-party admin generator is close to a free default and should be the starting recommendation.
  - For JS/TS full-stack stacks without a built-in admin (Next.js, Remix/React Router), the category needs a named third-party layer: a headless framework (Refine) that generates CRUD UI on top of an existing API/data layer with full code ownership, or an auto-generated admin UI bound directly to the DB/ORM models (AdminJS). React Admin is the older, still-maintained option for building a fully custom admin SPA against a REST/GraphQL API rather than generating one.
  - **Decision rule to carry into the skill**: if the backend framework has a mature first-party admin (Django Admin, Filament, Avo/ActiveAdmin) and the internal tool's needs stay close to "CRUD over the data model," use it — building a custom admin panel from scratch duplicates work the framework already does well. Reach for Refine/AdminJS/React Admin only when the admin needs custom workflows or a JS/TS-only backend has no first-party option. Reach for a no-code/low-code tool (Retool-style) only for internal tools with no need to ship as part of the product codebase — out of scope for this baseline (see below).

## Explicitly out of scope

- **No-code/low-code internal-tool builders (Retool, Appsmith, etc.)** — why excluded: these are a different category of solution (build vs. buy for the *entire* internal tool, not a library choice within a codebase) and the prompt's target is code-owned skill guidance for a project's own stack, not tool procurement advice.
- **Full event-sourcing/CQRS as the primary architecture** — why excluded: covered as a targeted technique layered inside the modular-monolith default (for the audit-log and reporting sub-cases specifically), not re-derived as a top-level architecture choice — that ground is already covered by architecture-templates.md.
- **Mobile-app frontend architecture** — why excluded: category definition is web business apps (SaaS/back-office); mobile client architecture is a distinct concern with its own baseline needs, not covered here.
- **Detailed database schema/indexing design** — why excluded: this is data-layer implementation detail, not an architecture-selection signal; belongs in implementation guidance, not this baseline.
- **Billing/subscription/metering architecture** — why excluded: adjacent but large enough to be its own sub-topic; flagged as an open question below for whether it belongs in this skill or a separate one.
