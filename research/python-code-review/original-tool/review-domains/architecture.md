# Architecture Review Domain

## Scope
Reviews structural design, separation of concerns, database access patterns,
API design, deployment configuration, and infrastructure readiness.

## Tier Applicability
| Check | Script | Web | Enterprise |
|-------|--------|-----|------------|
| Separation of concerns | Yes | Yes | Yes |
| Dependency injection | No | Yes | Yes |
| DB user segregation | No | Yes | Yes |
| API endpoint design | No | Yes | Yes |
| Health/ready endpoints | No | Yes | Yes |
| Middleware stack | No | Yes | Yes |
| Dockerfile review | No | Optional | Yes |
| Reverse proxy config | No | No | Yes |
| Service mesh / mTLS | No | No | Yes |
| Network topology | No | No | Yes |

## Review Criteria

### Critical
- Database admin credentials used for application read/write operations
- Production app server is Flask/Django dev server (`flask run`, `manage.py runserver`)
- Docker container running as root user in production

### Important

**Separation of Concerns**
- Business logic free of framework-specific objects (no raw Request objects in service layer)
- Controllers/views extract scalar values, pass to service functions
- Data access layer separated from business logic
- Configuration isolated (not scattered as inline constants)

**Database Architecture**
- 3-user segregation: readonly (GET APIs), writer (POST/PUT/DELETE), admin (migrations)
- Connection pool configured: `pool_size=5`, `max_overflow=10`, `pool_timeout=30`,
  `pool_recycle=3600`, `pool_pre_ping=True`
- Migration scripts have both `upgrade()` and `downgrade()` functions
- Autogenerated migrations manually reviewed (flag if migration file looks untouched)
- Dual-identifier pattern suggested for public-facing APIs: integer PK internal,
  UUID/NanoID for external exposure

**API Design (web/enterprise)**
- `/health` endpoint: status, timestamp, version, uptime, memory, cpu
- `/ready` endpoint: readiness checks (DB connectivity, downstream services)
- URL-path-based API versioning (`/api/v1/...`)
- Search/lookup endpoints have `min_score` (default 70) and `max_output_records`
  (default 10) parameters
- Consistent error response format with error codes

**Middleware (web/enterprise)**
- CORS configured (not wildcard `*` in production)
- TrustedHostMiddleware present
- Request/response logging middleware
- Rate limiting configured
- JWT or equivalent auth middleware

**Deployment (enterprise)**
- Dockerfile uses multi-stage build (builder -> runtime)
- Build tools (gcc, make) not present in final image
- Distroless or minimal base image preferred
- Non-root user created and used (`USER appuser`)
- Worker count calculated: `(2 * CPU_CORES) + 1` for sync, or documented for async
- `max_requests` + `max_requests_jitter` configured for memory leak mitigation
- Reverse proxy (nginx/ALB) in front of app server, not direct exposure
- SSL/TLS termination at proxy level

**ASGI/WSGI Configuration (web/enterprise)**
- FastAPI/Starlette -> Uvicorn workers managed by Gunicorn (`-k uvicorn.workers.UvicornWorker`)
- Django/Flask -> Gunicorn with appropriate worker class
- Worker timeout configured (30s default)
- Header size limits configured (`limit_request_field_size`)

### Minor
- API documentation auto-generated (OpenAPI/Swagger)
- Database schema documented or visualized
- Architecture Decision Records (ADRs) present for major choices
- README includes architecture overview or diagram

## Scoring Guide
- 10: Clean separation, DB segregation, health endpoints, secure deployment
- 8-9: Good separation, most patterns followed, minor deployment gaps
- 6-7: Some separation issues, missing health endpoints or DB segregation
- 4-5: Business logic coupled to framework, no DB segregation, dev server in prod
- 1-3: Monolithic with no separation, admin creds for app, no deployment config
